Chapter 3: Methodology and System Design

3.1 Introduction

This chapter details the methodology, architectural design, deployment topology, data models, and cryptographic mechanisms employed in developing the system. The primary goal of the system is to establish a secure, digital logbook workflow where internship entries are cryptographically sealed upon supervisor approval. Once sealed, these records are rendered immutable and verifiable by any external third party via public endpoints, without compromising personal data or exposing internal database nodes.

The implementation details documented in this chapter represent the actual, deployed structure of the project. Key system evolutions—such as the transition from the initially specified Angular frontend to a React 18 and TypeScript Single Page Application (SPA), and the transition from a shared symmetric Hash-based Message Authentication Code (HMAC) to an asymmetric public-key cryptography scheme (Ed25519)—are fully outlined and justified.

3.2 Design Methodology (Agile / Scrum Framework)

To ensure iterative progress, rapid deployment cycles, and tight alignment between functional requirements and technical execution, an Agile / Scrum framework was adopted as the development methodology. The project was decomposed into a planned release lifecycle consisting of 6 development sprints, managing a total of 153 story points.

3.2.1 Agile/Scrum Development Workflow

The Scrum model relied on rapid feedback loops and strict milestones. The iterative workflow followed a structured loop:

The Scrum team enforced clear boundaries to maintain high code quality:

Definition of Ready (DoR): A user story was marked ready for development only if it was uniquely identified, sized in story points, mapped directly to specific software requirements specification (SRS) clauses, and had explicit, testable acceptance criteria.

Definition of Done (DoD): A story was considered done only when the code was fully compiled and type-checked without errors, integrated into the monorepo, verified locally under simulation, merged into the main branch, and verified in the production environment.

3.2.2 Sprint Execution and Milestone Scope

The 153 story points were distributed across 6 sprints to manage development complexity and ensure a logical construction sequence:

Sprint 1 — Foundation & Identity (24 pts): Scaffolding of the monorepo, database migrations setup, creation of core security schema, and implementation of domain-gated registration, email verification, and Argon2id session authorization.

Sprint 2 — Logbook Core & Access Control (23 pts): Construction of role-based access control (RBAC) middleware, development of the internship profile interface, creation of daily log entry drafts, and implementation of the attachment pipeline using direct-to-cloud signed URLs.

Sprint 3 — Review, Sealing & Audit Chain (23 pts): Creation of supervisor review queues, implementation of one-at-a-time entry decisions, design of the Ed25519 signature generator, and creation of the hash-chained, transaction-locked database audit log.

Sprint 4 — Public Verification & Progress (25 pts): Implementation of the anonymous verification page, design of the token-to-seal mapping model, rendering of dynamic QR blocks on verified items, and development of live progress tracker dashboards.

Sprint 5 — Corrections & Reports (28 pts): Engineering of versioned append-only entry corrections, development of server-side PDF generation using pdf-lib (compiled with aggregate signature hashes and dual verification QRs), and design of academic assessment forms.

Sprint 6 — Admin, Privacy, Audit & Hardening (30 pts): Creation of administrative control panels (user management, key rotation, token revocation), development of the database crypto-shredding engine for data-protection compliance, and execution of final production code audits.

3.3 High-Level System Architecture & Deployment Topology

The system is built as an integrated monorepo designed to prioritize low-latency execution, high cryptographic reliability, and secure third-party validation. The architectural layout separates static user interface layers from transaction services and persistent storage networks.

The system components interact across three core layers:

Frontend Single Page Application (SPA): Built using React 18, Vite, and TypeScript. It is deployed as a globally distributed static application on Vercel. The client maintains user session states, routes interface pages locally via React Router, validates user inputs prior to form dispatch, and processes client-side verification tasks.

Serverless RESTful API Server: Engineered with Node.js and Express.js. It compiles into a single unified serverless function handler to eliminate cold-start route latencies on serverless infrastructure. The backend processes database queries, executes cryptographic signing procedures, generates compiled PDF reports, and enforces system-wide security middleware.

Cloud-Native Infrastructure Ecosystem:

Neon Serverless Postgres: Serves as the primary relational database. Connection performance is managed through built-in connection pooling.

Vercel Blob Storage: Stores all binary logbook attachments (e.g., JPEG/PNG evidence files) and final compiled, sealed PDF files. By routing media payloads directly from the client via temporary signed upload tokens, the platform successfully bypasses the typical 4.5 MB body limit on serverless runtime functions.

Resend Service: Handles transaction emails, delivering sign-up validation links, account security reminders, password reset tokens, and supervisor digest notifications.

3.4 Architectural Subsystems & Design Layering

To ensure strict separation of concerns, the platform employs a modular design pattern across both the client and server codebases.

3.4.1 Client-Side Subsystem Architecture

The React application architecture isolates data representation from local state management and server-side synchronization:

API Connection Layer: Managed via TanStack Query (React Query). This layer caches server responses, handles asynchronous retry logic, manages mutations, and invalidates out-of-date cache states to ensure instant state sync.

Form & Validation Layer: Handled using React Hook Form combined with Zod schema resolvers. Schemas are cross-shared between the client and server codebases. This structure ensures input verification takes place on the client before dispatching network requests, preventing invalid data from reaching the API endpoints.

Design Token Layout: Implemented using modular CSS classes. The system features a custom, high-contrast palette tailored for accessibility, incorporating responsive card-based tables designed for both mobile and desktop screens.

3.4.2 Server-Side Architectural Layering

The Express.js server adopts a clean, modular repository-pattern layout:

Routing Layer: Declares API endpoints and directs incoming HTTP requests to their designated controllers.

Middleware Layer: Intercepts requests to validate request schemas (Zod), verify JWT access tokens, handle session renewals, enforce Role-Based Access Control (RBAC) boundaries, and write operational events to the audit trail.

Service Layer: Executes core business logic, checks submission-window boundaries (such as the 7-day log entry submission limit), canonicalizes payloads, and calls the cryptographic signing modules.

Repository Layer (Drizzle ORM): Manages database interactions through typed schema files. It uses automatic migration scripts (drizzle-kit) to handle schema modifications safely while preventing manual database sync errors.

3.4.3 Role-Based Access Control (RBAC) & Route Scoping

The platform enforces a strict RBAC policy. Security contexts are embedded directly inside JWT payloads and evaluated by a dedicated route-scoping middleware:

Student Role: Granted permissions to manage personal internships, draft log entries, add attachments, submit log entries for supervisor review, issue version corrections, and export personal profile logs.

Industry Supervisor: Granted permissions to view only the students assigned to them within their supervisor directory. They can comment on submissions, approve entries (which locks the entry and triggers the cryptographic sealing workflow), or reject entries with a mandatory explanation.

Department Supervisor (Faculty): Granted read-only permission to access the compiled portfolios, log lists, and progress metrics of assigned students. They are authorized to write formal grading assessments but cannot alter sealed logs or access system credentials.

System Administrator: Granted complete system-wide management capabilities. This role handles user creation and deactivation, assigns student-to-supervisor mapping records, rotates verification keys, revokes compromised validation tokens, and processes data-erasure requests in compliance with data privacy regulations.

3.5 Database Schema Design & Relational Modeling

The relational model of the system is designed to enforce strict transactional consistency, support cryptographic verification tracking, and maintain regulatory compliance. The database structure consists of 14 tables.

3.5.1 Relational Schema Map (Entity-Relationship Layout)

The database layout also includes system orchestration tables that support academic tracking, operational auditing, and notification workflows:

internship_submissions: Tracks the workflow of compiled student portfolios submitted to the department for academic assessment.

assessments: Stores grade assignments and academic comments written by department supervisors for completed student placements.

notifications: Manages in-app status updates and tracks read states and email delivery.

audit_log: Holds sequential system event records. This table is strictly append-only and uses a continuous hash chain to guarantee log integrity.

3.6 Cryptographic & Security Engineering

VeriLog relies on a robust cryptographic architecture to guarantee data integrity, prevent unauthorized alterations, and enable independent verification.

3.6.1 Deterministic Payload Canonicalization (RFC 8785)

In relational database systems, JSON serialization is naturally non-deterministic. Compilers can vary property orderings, escape special character sequences differently, or alter whitespace padding. To ensure that identical data inputs always generate identical cryptographic signatures, the platform implements a strict RFC 8785-compliant canonicalization parser.

The serialization engine recursively walks through all input fields to sort object keys lexicographically, enforce strict formatting rules, strip whitespace, and validate data types:

The output is a stable, deterministic canonical byte string representing the core log properties:

$$C = \text{CanonicalStringify}(\{E_{\text{id}}, E_{\text{version}}, S_{\text{id}}, A_{\text{id}}, T_{\text{approved}}, D_{\text{attachments}}\})$$

3.6.2 Ed25519 Cryptographic Sealing Mechanics

The system uses asymmetric cryptography based on Ed25519 signatures. This approach allows any third party to independently verify logbook authenticity using only the published public key, eliminating the need to expose a shared database secret or maintain active database connections.

Let the message digest $D$ represent the SHA-256 hash of the canonical serialized log byte string $C$:

$$D = \text{SHA-256}(C)$$

Signature generation uses the private signing key ($sk$) via twisted Edwards curve operations over the prime field $\mathbb{F}_{2^{255}-19}$:

$$S = \text{Sign}(sk, D)$$

The output signature $S$ is represented as a compact pair $(R, s)$. This signature is stored alongside the log entry as a cryptographically secure seal, accompanied by its unique key identifier ($kid$).

To verify the seal, the signature $(R, s)$ is evaluated against the matching public key ($pk$) and the digest $D$:

$$[2^c \cdot s] B = 2^c R + \left[2^c \cdot \text{SHA-512}(R \parallel pk \parallel D)\right] pk$$

where $B$ is the curve base point and $c = 3$ represents the cofactor of the curve. If this relation holds, the log entry's authenticity, source identity, and content integrity are proven mathematically.

3.6.3 Audit-Trail Hash Chaining

To prevent database manipulation, VeriLog maintains a tamper-evident audit trail. This ledger is sequentially locked using recursive SHA-256 hashing:

The $n$-th cumulative hash sequence $H_n$ is computed as:

$$H_n = \text{SHA-256}(H_{n-1} \parallel \text{CanonicalStringify}(R_n))$$

where $R_n$ represents the current event metadata (actor, action, target type, target identifier, and payload properties), $H_{n-1}$ is the hash of the preceding log row, and $H_0$ is defined as $64$ consecutive zero characters to establish the genesis state.

To eliminate race conditions and fork errors during concurrent writes on serverless hosting, the system serializes all inserts. The database engine locks table execution during writes by calling a transactional PostgreSQL advisory lock:

This prevents database transactions from writing overlapping chains, guaranteeing a singular, linear ledger history.

3.6.4 Ghana DPA 2012 Compliance and Crypto-Shredding

To comply with global and national data privacy standards (such as the Ghana Data Protection Act, 2012), the system implements an append-only crypto-shredding pipeline. This process reconciles a user's right to erasure with the permanent, immutable nature of the cryptographic ledger.

When an erasure request is executed:

All identifying details (such as names, emails, activity descriptions, and supervisor comments) are cleared from tables and replaced with anonymous placeholder tombstones.

Evidence files and PDF uploads are permanently deleted from Vercel Blob Storage.

The cryptographic hashes, Ed25519 signatures, and timestamps are retained.

This design allows the public verification page to confirm that a valid, authentic log entry existed for the given date range without exposing personal information, satisfying both legal privacy requirements and technical system auditability.

3.7 Chapter Summary

This chapter detailed the methodologies, architectures, and security frameworks used to build the platform. By adopting a structured Agile/Scrum process, development progressed through planned, manageable sprints to deliver a secure, production-ready system. The platform uses a React 18 frontend and a Node.js Express serverless API deployed on Vercel. This setup is integrated with Neon Postgres connection pools and Vercel Blob Storage to bypass typical body size limits on serverless functions.

Finally, the system's security is guaranteed through a cryptographic design combining RFC 8785 canonicalization, Ed25519 digital signatures, transactional table locks on a serialized audit log, and a privacy-compliant crypto-shredding strategy. Together, these subsystems provide a modern, secure, and reliable alternative to paper-based internship recording.
